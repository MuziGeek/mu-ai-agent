## 分析 pgvector 构建初始化链路（只读分析，未改代码）

- 技术栈：Spring Boot 3.4.5 + Spring AI 1.1.8 + Alibaba DashScope（text-embedding-v3，1024 维）
- pgvector 走的是**纯自动配置**：`spring-ai-starter-vector-store-pgvector` →
  `PgVectorStoreAutoConfiguration`（after JdbcTemplateAutoConfiguration），
  条件 = `@ConditionalOnClass(PgVectorStore, DataSource, JdbcTemplate)` +
  `@ConditionalOnProperty(name=spring.ai.vectorstore.type, havingValue=pgvector, matchIfMissing=true)`
- DDL 在 `PgVectorStore.afterPropertiesSet()` 里执行，顺序：
  CREATE EXTENSION vector → hstore → uuid-ossp（仅 id-type=uuid 时）→ CREATE SCHEMA →
  （可选 DROP TABLE）→ CREATE TABLE → CREATE INDEX，**全部带 IF NOT EXISTS**
- 关键默认值（1.1.8，从字节码确认）：table=`vector_store`、schema=`public`、
  index=`spring_ai_vector_index`、id-type=uuid、index-type=hnsw、distance=cosine、
  `initializeSchema=false`、**`schemaValidation=false`**、`dimensions=-1`、
  fallback 维度 1536
- 建表模板：`CREATE TABLE IF NOT EXISTS %s (id %s PRIMARY KEY, content text, metadata json, embedding vector(%d))`

### 发现的问题（未修复）
1. `application-local.yml` 注释里的 `spring.ai.vectorstore.pgvector.enabled: false` 在 1.1.8 **不存在**此属性，禁用无效；正确写法是 `spring.ai.vectorstore.type: none`
2. `simple-vector` profile 下 PgVector 仍会创建（`@ConditionalOnMissingBean` 按返回类型 PgVectorStore 判定），且 RagApp/DocumentLoader 的参数名 `vectorStore` 与自动配置 bean 同名 → 实际注入仍是 PgVector，profile 切换形同虚设

4. 无 ApplicationRunner/CommandLineRunner/Controller 调用 `RagApp.initKnowledgeBase()`，知识库不会自动初始化
5. 表已存在时 `IF NOT EXISTS` 不会更新列定义，改维度（如 1536→1024）不生效，需手动 DROP/ALTER

## 实现批处理策略（BatchingStrategy）

### 结论：项目原本**没有**自定义批处理策略
- 全项目 grep `BatchingStrategy|batching|TokenCountBatching` → **零命中**
- 实际生效的是 `PgVectorStoreAutoConfiguration` 自带的默认策略
- `DocumentLoader` 里手动 `batchSize=10` 切片，就是绕开 DashScope 单次条数限制的临时手段

### 字节码核实的关键事实（Spring AI 1.1.8 + alibaba dashscope 1.1.2.1）
- `PgVectorStoreAutoConfiguration` 有 `@Bean @ConditionalOnMissingBean BatchingStrategy
  pgVectorStoreBatchingStrategy()` → `new TokenCountBatchingStrategy()`（无参）
- `PgVectorStore.doAdd()`：`embeddingModel.embed(docs, options, batchingStrategy)`；
  落库另按 `maxDocumentBatchSize`(10000) 切片 —— **两个上限是分开的**
- `DashScopeEmbeddingModel` 覆写了 3 参 `embed(...)`，但内部只是补默认 options 后
  `invokespecial AbstractEmbeddingModel.embed(...)` → 走 `EmbeddingModel` 的 default 方法
  → `for (batch : batchingStrategy.batch(docs)) { call(new EmbeddingRequest(texts, options)); }`
  → **每个批次 = 一次 DashScope 请求，策略真实生效**
- `EmbeddingModel` default 实现的 3 个要点：
  1. `Assert.notNull(documents, "Documents must not be null")`
  2. 逐批 `call()`，异常会中断整次 add
  3. **按位置回填向量** → 策略必须保序
- `TokenCountBatchingStrategy`：`MAX_INPUT_TOKEN_COUNT=8191`、`DEFAULT_TOKEN_COUNT_RESERVE_PERCENTAGE=0.1`；
  三参构造 → `(encodingType, max, reserve, Document.DEFAULT_CONTENT_FORMATTER, MetadataMode.NONE)`；
  实际预算 `Math.round((1-reserve) * max)`；**只按 token 切，条数无上限**；
  单文档超限抛 `IllegalArgumentException("Tokens in a single document exceeds the maximum number of allowed input tokens")`
- `jtokkit:1.1.0` 经 `spring-ai-tika-document-reader → spring-ai-commons` 传递引入（compile），
  未在 pom 里显式声明，直接 import `EncodingType` 可编译

### 改动
1. 新增 `rag/config/DashScopeBatchingStrategy.java`
   - 两级切分：先按 `maxDocumentsPerRequest` 分组，再委托 `TokenCountBatchingStrategy` 按 token 细分
   - 不复制子列表，用 `subList` 视图切片；保序拼接
   - 捕获委托器的 `IllegalArgumentException`，补上「哪个 `source` 文件超限 + 预估 token」再抛
     - 明细**刻意拼成单行**：异常信息常被塞进一行日志，带 `\n` 会打断日志格式（第一版踩过）
   - 日志：DEBUG 打印每组条数/预估 tokens/子批数；INFO 打印 `文档数 → 批次总数`
   - 自带 `JTokkitTokenCountEstimator` 仅用于日志与异常定位（口径与委托器一致：NONE + DEFAULT_CONTENT_FORMATTER）
2. 新增 `rag/config/EmbeddingBatchingConfig.java`：注册 `@Bean BatchingStrategy batchingStrategy(...)`，
   三个参数带默认值 `10 / 8000 / 0.1`，可用 `mu-ai.rag.batching.*` 覆盖
3. `DocumentLoader`：删掉手动 10 条切片循环，改 `vectorStore.add(allChunks)` 一次性提交
   - 单一事实来源：厂商限制只存在于策略一处
4. 新增 `src/test/java/com/muzi/muaiagent/rag/EmbeddingBatchingStrategyTest.java`（5 个用例）
   - 断言注入的 `BatchingStrategy` 是 `DashScopeBatchingStrategy`（覆盖机制静默失效的防线）
   - 12 文档 → `[10, 2]`；25 文档 → 保序且总数不变；超长文档抛异常且信息含 source；空/null 返回空批次

## 修复 IDEA 报「找不到符号 变量 log」（Lombok 注解处理器失效）

### 现象
- IDEA 编译报 `InterViewApp.java:150:9 java: 找不到符号 变量 log`
- 但源码里 `@Slf4j`（第 43 行）和 `import lombok.extern.slf4j.Slf4j`（第 8 行）都在
- **关键线索**：报错格式 `java: 找不到符号` 是 **IDEA 编译器**的输出（Maven javac 会带
  `[ERROR] ...java:[150,9]` 这种格式）→ 说明不是代码问题

### 定位过程
- `mvn -B clean compile` → **BUILD SUCCESS**，确认代码与 pom 对 Maven 都正常
- 读 `.idea/compiler.xml` → 找到元凶：
  `<entry name="$PROJECT_DIR$/../../Scoop/apps/maven/3.9.16/rep/org/projectlombok/lombok/unknown/lombok-unknown.jar" />`
  → 版本被解析成 **`unknown`**，指向不存在的 jar（`Test-Path` 返回 False）
- 本地仓库实际只有 `1.18.38`；`lombok/unknown/` 下仅两个 `.lastUpdated` 空壳文件

### 根因
`pom.xml` 里 `maven-compiler-plugin` 的 `<annotationProcessorPaths><path>` **没写 `<version>`**：
- Maven：缺 version 会回溯 dependencyManagement（spring-boot-dependencies 管理 lombok）→ 正常
- IDEA：**不回溯父 POM**，版本解析为 `unknown` → 生成无效 processorPath →
  Lombok 处理器根本没加载 → 不生成 `log` 字段

### 修复（两处）
1. `pom.xml`（根治）：`<path>` 内加 `<version>${lombok.version}</version>`
   - 先 grep 确认 `spring-boot-dependencies-3.4.5.pom:125` 有 `<lombok.version>1.18.38</lombok.version>`
   - 附详细注释说明「为什么不能省」
2. `.idea/compiler.xml`（止血）：把路径里的 `unknown/lombok-unknown.jar`
   改为 `1.18.38/lombok-1.18.38.jar`
   - `workspace.xml` 里无注解处理相关配置（已 grep 确认），无需改

### 验证
- `mvn -B clean compile` → BUILD SUCCESS
- `mvn -B help:effective-pom` → **三处** `annotationProcessorPaths`（default-compile、
  default-testCompile、plugin 级 configuration）**全部**插值为 `<version>1.18.38</version>`
- `mvn -B test -DexcludedGroups=llm` → Tests run: 11, Failures: 0，BUILD SUCCESS
